## 1. Hintergrund der Entscheidung

Free-Projekte bei Supabase werden bei geringer Aktivität über 7 Tage **pausiert, nicht gelöscht**. Nach der aktuellen Doku sind pausierte Free-Projekte bis zu 1 Jahr wiederherstellbar (frühere Angabe: 90 Tage), danach nur noch als Backup-Download. Gelöscht ist erst, was der Nutzer selbst löscht. Das Risiko ist also Ausfall nach Inaktivität, nicht Datenverlust. Gegenmaßnahmen sind Teil dieses Auftrags (3.8).

## 2. Festgelegte Entscheidungen (nicht neu verhandeln, aber im PR bestätigen)

| Thema | Entscheidung |
|---|---|
| Hosting der App | bleibt GitHub Pages, Hash-Router, unverändert |
| Backend | Supabase (Postgres + Auth + PostgREST), **ein Projekt pro Haushalt**, keine Mandantenlogik |
| Client | **Eigener kleiner `fetch`-Client**, kein `@supabase/supabase-js` (Größenbudget, analog zum Verzicht auf Octokit). Wenn sich zeigt, dass das unverhältnismäßig aufwendig ist: SDK per `import()` nachladen und im PR begründen |
| Anmeldung | Supabase Auth mit E-Mail und Passwort, **Registrierung im Projekt deaktiviert**, die zwei Konten legt der Nutzer im Dashboard an |
| Datenmodell | **Ereignisprotokoll bleibt** (Tabelle `events`, nur anhängen), Fold und Konfliktlogik wie im Plan. Keine normalisierten Fachtabellen |
| Pull | Server-Cursor `seq` (bigserial). Polling wie im Plan (App-Start, sichtbar, online, 2 s nach lokaler Änderung, 60 s im Vordergrund). Realtime ist **nicht** Teil von M2 |
| Idempotenz | Push per Insert mit „Duplikate ignorieren“ auf `id`, Wiederholung ist immer sicher |
| Zugriffsschutz | Row Level Security, nur Mitglieder des Haushalts, Ereignisse append-only (kein Update, kein Delete) |
| Laufzeit-Eingaben | Projekt-URL, öffentlicher Schlüssel (anon/publishable), E-Mail, Passwort: **nur zur Laufzeit eingeben**, nie im Repo, nie in Build-Variablen |

### 3.2 Transport: `src/data/remote/`

```ts
export interface SyncTransport {
  signIn(email: string, password: string): Promise<Session>;
  refresh(): Promise<Session>;                          // Refresh-Token einlösen
  getHousehold(): Promise<HouseholdRow | null>;         // null = noch nicht eingerichtet
  createHousehold(h: HouseholdInput): Promise<HouseholdRow>;
  pushEvents(events: WireEvent[]): Promise<void>;       // idempotent
  pullEvents(afterSeq: number, limit: number): Promise<Array<WireEvent & { seq: number }>>;
  keepAlive?(): Promise<void>;
}
```

- `supabase-transport.ts` (eigener Client auf `fetch`), `memory-transport.ts` (Tests, simulierbar: Offline, Auth abgelaufen, Duplikate, Verzögerung), **eine** gemeinsame Vertragstestsuite gegen beide (Supabase mit gemocktem `fetch`).
- Fehlerklassen: `AuthError` (401, Refresh fehlgeschlagen), `ForbiddenError` (RLS/403), `RateLimitError`, `NetworkError`, `ServerError` (5xx). Texte nach M1-Muster, **nie** Token, Schlüssel, URL oder Antwortkörper in Fehlermeldungen oder Logs.
- Access-Token automatisch per Refresh-Token erneuern (einmal pro 401, dann Auth-Fehler). Refresh-Token rotiert: neuen Wert sofort persistieren, parallele Refreshs serialisieren.
- Alle Anfragen gehen nur an die eingegebene Projekt-URL (Format prüfen, `https://`, Host auf `*.supabase.co` beschränken, damit die CSP eng bleibt). Kein anderer Host.
- Pull seitenweise (z. B. 500 pro Seite), bis weniger zurückkommt als `limit`.

### 3.3 SQL: `supabase/migrations/0001_init.sql`

Nur Schema, keine Daten, keine Namen. Wird vom Nutzer im SQL-Editor oder per CLI eingespielt (im README beschreiben, nicht automatisieren).

- `household` (genau eine Zeile erzwingen, z. B. `id boolean primary key default true check (id)`): Format-Version, `householdId`, `createdAt`, Einstellungen (`name`, `placeLabel`, `periodStart`, `periodEnd`, `baseCurrency`, `secondCurrency`, `fxProvider`).
- `members`: `user_id uuid primary key references auth.users`, `display_name`, `color`, `locale`, `theme`; höchstens 2 Zeilen (Constraint oder Trigger).
- `events`: `seq bigint generated always as identity`, `id uuid primary key`, `v int`, `hlc text`, `device uuid`, `author uuid`, `entity text`, `row_id uuid`, `op text`, `base uuid[]`, `data jsonb`, `received_at timestamptz default now()`; Index auf `seq`.
- RLS auf allen Tabellen aktiv. Mitglied = `auth.uid()` steht in `members`. `events`: `select` und `insert` für Mitglieder, bei `insert` zusätzlich `author = auth.uid()`. **Kein** `update`/`delete`. `members`: Lesen für Mitglieder, Schreiben nur eigene Zeile. `household`: Lesen für Mitglieder; Anlegen nur, solange keine Zeile existiert und der Anleger sich als erstes Mitglied einträgt (per `security definer`-Funktion `setup_household(...)`, sauber begründet und mit `search_path` gesetzt).
- Der zweite Nutzer wird vom Nutzer im Dashboard angelegt und von der ersten Person in der App als Mitglied eingetragen (Funktion `add_member(...)`, nur für bestehende Mitglieder, max. 2). Lies dafür die Supabase-Doku zu Auth-Nutzern und prüfe, wie sich die `user_id` der zweiten Person zuverlässig ermitteln lässt, ohne E-Mails im Repo zu speichern. Wenn keine saubere Lösung existiert: einfachste sichere Variante wählen (z. B. zweite Person trägt sich beim ersten Login selbst ein, solange `members` < 2 **und** die erste Person den Haushalt freigegeben hat) und im PR begründen.
- Eine Datei `supabase/README.md` mit den manuellen Schritten und einer **RLS-Prüfliste** (Anmeldung mit Konto A, Konto B, ohne Anmeldung, mit fremdem Konto: was darf lesen/schreiben). Zusätzlich ein SQL-Skript `supabase/tests/rls-check.sql` zum Selbstprüfen im SQL-Editor. Automatisierte Postgres-Tests sind **nicht** gefordert (keine Docker-Abhängigkeit).

## 5. Stolpersteine

- **Refresh-Token rotieren**: zwei gleichzeitige Refreshs verbrauchen sich gegenseitig. Serialisieren und sofort persistieren, sonst wird die Sitzung ungültig.
- **Öffentlicher Schlüssel ist kein Geheimnis, aber trotzdem nicht ins Repo**: Er steht in keiner Datei, keinem Test, keinem Workflow-Klartext, nur in Secrets und zur Laufzeit.
- **RLS ist die einzige Sicherheitsgrenze.** Die App-Logik ist kein Schutz. Jede neue Tabelle bekommt RLS im selben Commit.
- **`security definer`-Funktionen** immer mit gesetztem `search_path` und minimalen Rechten.
- **Pages-Origin teilen sich alle Projektseiten eines Kontos**: Der gespeicherte Refresh-Token ist dort lesbar. Keine weiteren Pages-Seiten mit Fremdcode unter diesem Konto (Hinweis in README beibehalten).
- iOS: Home-Bildschirm-App und Safari haben getrennten Speicher, `persist()` weiter bei jedem Start. Eingaben mindestens 16 px.
- Hash-Router plus `base`: Links und Assets relativ bzw. über `import.meta.env.BASE_URL`.
- `localStorage` immer in try/catch.
- Ahorn-Rot nur für Aktion und Auswahl. Warnungen Amber + Icon + Text.
- Keine Kommentare oder Texte mit echten Namen, auch nicht als „Beispiel“.
