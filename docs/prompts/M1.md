### 3.7 Speicherschicht: `src/data/remote/`

```ts
export interface RemoteFile { path: string; sha: string; text: string }
export interface RemoteStore {
  whoAmI(): Promise<{ login: string }>;
  checkRepoAccess(): Promise<void>;                      // wirft NoAccessError
  headCommit(): Promise<{ sha: string; changed: boolean }>; // changed=false bei 304
  listFiles(prefix?: string): Promise<Array<{ path: string; sha: string }>>;
  readFile(path: string): Promise<RemoteFile | null>;
  writeFile(path: string, text: string, prevSha: string | null, message: string): Promise<{ sha: string }>;
}
```
Fehlerklassen: `AuthError` (401), `NoAccessError` (404 auf Repo), `RateLimitError` (403/429 mit Rate-Limit-Headern, inkl. Reset-Zeit), `ConflictError` (409/422 wegen veralteter SHA), `NetworkError`.

`github-store.ts` (eigener kleiner Client auf `fetch`, kein Octokit):
- Basis `https://api.github.com`, Header `Authorization: Bearer <token>`, `Accept: application/vnd.github+json`. Den aktuellen Wert für `X-GitHub-Api-Version` in der GitHub-REST-Doku nachsehen. Wenn unklar, Header weglassen.
- `whoAmI`: `GET /user`. `checkRepoAccess`: `GET /repos/{owner}/{repo}`.
- `headCommit`: `GET /repos/{o}/{r}/git/ref/heads/main` mit `If-None-Match` (ETag im Speicher halten). `304` → `changed: false`. Bedingte Anfragen mit 304 zählen nicht gegen das Rate-Limit.
- `listFiles`: `GET /repos/{o}/{r}/git/trees/{commitSha}?recursive=1`, nur `type: 'blob'`.
- `readFile`: `GET /repos/{o}/{r}/contents/{path}` (404 → `null`). Inhalt aus Base64 **UTF-8-korrekt** dekodieren.
- `writeFile`: `PUT /repos/{o}/{r}/contents/{path}` mit `{ message, content (Base64, UTF-8-korrekt, für große Strings in Chunks), sha? }`. Veraltete SHA → `ConflictError`.
- Pfade segmentweise mit `encodeURIComponent` kodieren.
- Der Token darf **nie** geloggt, in Fehlermeldungen übernommen oder an einen anderen Host gesendet werden.

`memory-store.ts`: gleiche Schnittstelle im Speicher, mit simulierbaren Fehlern (Konflikt, Offline, Auth) für Tests.

`remote-store.contract.test.ts`: **eine** Testsuite, die gegen beide Implementierungen läuft (GitHub über gemocktes `fetch`). Dazu GitHub-spezifische Tests: ETag/304, Base64 mit Umlauten und Emoji, Fehlerzuordnung, Token taucht in keiner Fehlermeldung auf.

## 5. Stolpersteine

- Hash-Router plus `base`: Links und Assets immer relativ bzw. über `import.meta.env.BASE_URL`, nie absolut `/…`.
- iOS: Home-Bildschirm-App und Safari haben getrennten Speicher. Eingaben brauchen mindestens 16px Schrift (sonst Zoom). Safe Areas oben und unten beachten (`black-translucent` lässt Inhalte unter die Statusleiste laufen).
- Base64: `btoa`/`atob` können kein UTF-8. Über `TextEncoder`/`TextDecoder` und Byte-Arrays gehen.
- GitHub Contents-API: Beim Anlegen kein `sha` senden, beim Ändern die aktuelle `sha` der Datei. Antworten können verzögert konsistent sein. Nach `writeFile` die zurückgegebene `sha` verwenden, nicht neu lesen.
- Dexie in Tests: `fake-indexeddb/auto` in der Vitest-Setup-Datei.
- `localStorage` kann in privaten Fenstern werfen: immer try/catch.
- Ahorn-Rot (`--acc`) nur für Aktionen und Auswahl. Fehlermeldungen im Formular in `--label` mit `warn`-Icon in `--warn`, nie rot.
- Keine Kommentare oder Texte mit echten Namen, auch nicht als „Beispiel“.
