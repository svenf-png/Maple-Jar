# Auftrag: Maple Jar, Meilenstein M4 (Projektion, Szenarien, Desktop-Ansichten)

M1 bis M3 sind gemergt. Dieser Auftrag hat **zwei Teile mit je eigenem Branch und Draft-PR**:

- **Teil A:** Daten und Logik für Projektion und Szenario (Schema, Fold, Dexie, Domain, Aktionen), vollständig getestet, ohne neue Oberfläche.

## 1. Festgelegte Entscheidungen (nicht neu verhandeln)

| Thema | Entscheidung |
|---|---|
| Projektion | Einnahmen minus Fixkosten minus Sparen minus variable Ausgaben, pro Kalendermonat von `periodStart` bis `periodEnd`, kumuliert ab 0 |
| Ist und Prognose | Tage bis einschließlich heute sind Ist, Tage danach Prognose. Monate vor dem laufenden sind `actual`, der laufende `current`, spätere `forecast` |
| Nicht doppelt zählen | Eine Fixkosten-Fälligkeit zählt genau einmal: gebucht als Eintrag, sonst als Fälligkeit (dieselbe Regel wie `income-split.ts`, inkl. Abdeckung durch verwaiste Einträge). Variable Ausgaben sind nur Einträge mit `source: 'manual'` |
| Variable Prognose | Durchschnitt pro Kategorie über die bis zu 3 vollständigen Kalendermonate vor dem laufenden Monat, frühestens ab dem Monat des ersten manuellen Eintrags. Gibt es keinen solchen Monat: Budgetlimit des laufenden Monats je Kategorie (`variableBasis: 'budget'`), sind auch die 0: `'none'`. Anteilig nach Prognosetagen im Monat |
| Sparen | Fixkosten mit `isSaving` und positive Sparziel-Beiträge. Entnahmen (negative Beiträge) zählen nicht (wie im Kreisdiagramm) |
| EUR | Einträge mit eigenem Kurs, geplante EUR-Beträge (Einnahmen, Fixkosten, Beiträge, Szenario-Extras) mit dem bekannten Kurs; ohne Kurs zählen sie 0. Beides setzt `approximate` |
| Szenario (Frage 4) | **Ein** gemeinsames gespeichertes Arbeitsszenario, feste Zeilen-ID `SCENARIO_ID`, Last-Write-Wins ohne Konfliktdialog. Kein Name (es gibt nur eines) |
| Regler (Frage 10) | pro Kategorie −50 bis +50 % in 5er-Schritten, wirkt nur auf die variable Prognose |
| Extras | Einmalausgabe (`expense`, Datum `on`) zählt variabel im Monat von `on`, nur wenn `on` nach heute liegt. Neues Ziel (`goal`, Zielbetrag, `on` bis `targetDate`) wird als Sparen gleichmäßig auf `max(1, monthsBetween(on, targetDate))` Monate ab dem Monat von `on` verteilt, nur Monate ab dem laufenden zählen |
| Als Budgets übernehmen | ab dem **nächsten** Monat: Basis = gültiges Limit, sonst der Kategorie-Durchschnitt; neu = Basis × (100 + %) / 100, auf ganze Währungseinheiten (100 Minor) gerundet. Übernommene Kategorien verlieren danach ihren Reglerwert |
| Schema | `scenario` ist additiv (alte Geräte parken es in „Diagnose“). Die SQL-Tabelle `events` erlaubt `scenario` bereits. Bestehende Entitäten bleiben unverändert, also keine Schema-Version 2 |

## 2. Teil A: Umfang

1. **Schema** `scenario`: `categoryPct` (Objekt Kategorie-UUID → Ganzzahl −50..50, Vielfaches von 5, höchstens 200 Schlüssel), `extras` (Liste, höchstens 50, je `id` UUID, `kind` `expense`|`goal`, `name` 1..80 Zeichen, `amountMinor` > 0, `currency`, `on`, bei `goal` Pflichtfeld `targetDate > on`, bei `expense` kein `targetDate`). `update` nur geänderte Felder, `delete`/`restore` wie üblich.
2. **Fold/Dexie:** `scenario` in `ENTITIES` und `FOLD_ORDER`, nicht in `CONFLICT_ENTITIES`. Dexie Version 4 mit Tabelle `scenario: 'id'`, Migration ohne Datenverlust.
3. **Domain** `projection.ts` und `scenario.ts`, rein und vollständig getestet.
4. **Aktionen** `saveScenario`, `adoptScenarioBudgets`, Hook `useScenario`.
5. `docs/PLAN.md` Tabelle 2.3 (`scenario`) an die Felder anpassen.

Definition of Done Teil A: `lint`, `typecheck`, `test`, `build`, `check:size`, `check:privacy` grün, Draft-PR mit Zusammenfassung und Abweichungen.
